## Context

See `proposal.md` for motivation. Platform's public route table is the anti-drift source for handlers and OpenAPI. Session principals are resolved before handlers. Generic domain proxy routes stream authenticated requests but intentionally leave service-owned paths and schemas opaque; Knowledge's current loopback search accepts explicit tenant input and uses internal error JSON, so publishing it directly would violate the public boundary.

## Goals / Non-Goals

**Goals:**

- Present a minimal typed library API to every client surface.
- Make caller identity the only source of tenant authority.
- Reuse the configured single-host Knowledge address and bounded HTTP infrastructure.
- Keep availability truthful through capability discovery and safe error mapping.

**Non-Goals:**

- Copying search documents or user-content state into Platform schemas.
- Creating operations, outbox records, or event contracts for synchronous query/state resources.
- Documenting every generic `/v1/k` proxy path in Platform OpenAPI.

## Decisions

### D1: Dedicated handlers call a dedicated Knowledge client

A `library` public module owns request validation, public types, handlers, and route docs. A narrow internal client uses the configured `knowledge` loopback address but constructs fixed `/internal/search` and `/internal/user-content/command` requests; the caller cannot select either path or tenant. It applies the existing control-class body and timeout budgets.

Extending the generic proxy was rejected because it would pass through service-private paths and responses. Persisting a Platform projection was rejected because it would create a second owner and stale read state.

### D2: Public validation and response minimization happen at Edge

Query deserialization rejects unknown fields, bounds query Unicode length, validates read state and page values, and refuses any tenant selector before delegation. The client decodes a strict Knowledge response, rejects non-finite scores, truncates/validates title and snippet bounds defensively, and maps only public fields. `analysis_id` remains opaque to clients even though it is a UUID.

### D3: PUT is synchronous and naturally idempotent

`PUT /v1/library/items/{analysis_id}/read-state` validates the path/body, derives the tenant, and calls Knowledge's read-state-only command. It does not create an operation or use the idempotency ledger because replacing the complete small state resource is already idempotent. Retryable transport uncertainty is represented by the normal dependency error envelope.

### D4: Capability requirements add last-observed Knowledge health

The deployment snapshot gains a finite Knowledge-available fact derived from the existing background service-capability observation, not a request-path probe. `library.search` and `library.read_state` require both database-backed session authentication and healthy Knowledge. The metrics loop samples both closed names on every tick, including zero.

### D5: OpenAPI remains generated from the route table

Both endpoints and their schema types are registered in `crates/api-doc`; the checked-in `openapi/openapi.json` is regenerated by the existing tool. Generated-client consumers update only after this producer contract lands.

## Risks / Trade-offs

- [The generic gateway and dedicated client share a destination] -> fixed route construction and tests assert no public path/headers are forwarded and no duplicate service configuration is introduced.
- [Knowledge returns oversized or malformed data] -> strict bounded decoding maps it to `upstream_invalid_response` before public serialization.
- [Capability observation lags a failure] -> the request still has bounded failure mapping; capabilities are advisory availability, never a success cache.
- [Synchronous search can consume Edge resources] -> small body/page bounds, pooled loopback connections, total deadlines, and no fan-out keep work finite.

## Migration Plan

Deploy after the compatible Knowledge change. Verify capability names remain absent against the old/unhealthy dependency and appear only after the new dependency is healthy. Regenerate OpenAPI before client work. Roll Platform back after Telegram; Knowledge can remain forward-compatible.
